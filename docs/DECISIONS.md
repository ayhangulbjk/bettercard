# Decisions

Architectural choices and why they were made. Each is reversible; the record
exists so a reversal is deliberate rather than accidental.

## D-1: Flutter and Dart versions, and what verification found

**Decision.** Target `sdk: >=3.4.0 <4.0.0`, `flutter: >=3.22.0`. Verified
against Flutter 3.47.9 / Dart 3.13.7 on Windows, 2026-10-31.

**History.** The scaffold was authored on a machine with no Dart or Flutter
toolchain at all, so it was written to maximise the chance of compiling
unmodified: dependencies limited to `flutter`, `flutter_riverpod` and `meta`,
and two version-sensitive APIs avoided on purpose.

- `cardTheme` is not set, because its type changed from `CardTheme` to
  `CardThemeData` across releases. Panels use `AppPanel` instead.
- `Color.withOpacity` and `Color.withValues` are both avoided, since the first
  is deprecated on new Flutter and the second absent on older. Literal ARGB
  values are used.

**What verification actually found.** The toolchain was installed afterwards
and the code compiled with two analyzer infos and no errors: one
`prefer_const_constructors` and one `unnecessary_nullable_for_final_variable_declarations`,
both fixed. The declared constraints resolve cleanly on Dart 3.13.7 and
`flutter_lints ^4.0.0` still resolves despite 6.x being current.

The costly defects were not compile errors but **layout** errors, and they were
invisible until the widget tests were moved to a portrait viewport. See D-13.

**Consequence.** The avoidance measures above remain worthwhile, but note that
`AppPanel`, introduced to dodge `cardTheme`, carried its own defect (D-13).
Avoiding a framework API means taking on what that API was doing for you.

## D-2: Flame is not a dependency

**Decision.** Build the presentation layer from plain Flutter widgets. Do not
add `flame`, even though it was named in the requested stack.

**Why.** Flame is a game loop, a component tree and a renderer for games that
need continuous simulation. A trick-taking card game is a sequence of discrete
states with transition animations. Everything the table needs - layout,
hit-testing, implicit animations, accessibility, text scaling - is better
served by widgets, and Flutter's widget tree already provides it. Adding Flame
would mean reimplementing hit-testing and semantics inside a canvas, and the
instruction to avoid unnecessary dependencies applies.

**Revisit if.** Particle effects, continuous physics or a shader-driven table
turn out to matter for the feel. Flame can then be introduced for the table
surface alone, without disturbing the domain.

## D-3: The dependency list is three entries

**Decision.** `flutter`, `flutter_riverpod`, `meta`. Dev: `flutter_test`,
`flutter_lints`.

**Why.** The native host folders are generated by `flutter create .` and are
not committed, so no plugin can be registered yet. Any plugin dependency would
be unresolvable or unbuildable in this state. `meta` is declared explicitly
rather than taken transitively, because `depend_on_referenced_packages` would
flag it and because the domain must not reach into `package:flutter` for
`@immutable`.

`go_router` was not added: the app is a handful of full-screen destinations
with no deep links and no web target, so named routes on `Navigator` solve it
without introducing a new concept.

## D-4: Persistence is an interface with an in-memory implementation

**Decision.** `SettingsRepository` with `InMemorySettingsRepository`, plus a
`SettingsCodec` that is fully real and tested.

**Why.** See D-3: no storage plugin can be registered yet. The interface keeps
the entire pipeline - model, codec, provider, UI - real and testable now, and
the disk implementation drops in behind it with no change above. The settings
screen says plainly that settings do not survive a restart, rather than
implying that they do.

## D-5: The project owns its random number generator

**Decision.** `SeededRandom`, xorshift64* with a SplitMix64 seed finalizer,
instead of `dart:math` `Random(seed)`.

**Why.** The `Random` algorithm is an SDK implementation detail that is allowed
to change between Dart releases. If it did, every saved match would replay
differently and every benchmark baseline would silently become incomparable.
Owning the generator makes reproducibility a property of this repository rather
than of the toolchain.

`nextInt` uses rejection sampling rather than modulo, so the shuffle carries no
bias, which matters for an app whose selling point is fair opponents. The seed
passes through a SplitMix64 finalizer so that seeds 0, 1 and 2 produce
well-separated streams instead of correlated ones; consecutive deals would
otherwise feel repetitive.

## D-6: Localisation is an interface, not ARB files

**Decision.** `AppStrings` as an abstract interface with `TurkishStrings`
implementing it. No `intl`, no code generation, no ARB.

**Why.** Every user-visible string already goes through the seam, which is the
expensive part of retrofitting localisation. Code generation adds a build step
and a dependency that, with a single locale, buys nothing. Adding English means
one more implementation and one more arm in `stringsProvider`.

**Revisit if.** A third locale arrives, or plural and gender rules start
appearing. Then move to ARB; the call sites do not change.

## D-7: Source files are ASCII-only

**Decision.** Turkish UI copy in `strings_tr.dart` is written without
diacritics: `Baslangic`, not the correctly accented form.

**Why.** This is a **known compromise, not a preference.** The scaffold was
authored through a toolchain where writing non-ASCII bytes into source could
not be done reliably, so encoding-mangled strings were the real risk.
Diacritic-free Turkish is readable; mojibake is not.

**Action required.** Restore proper Turkish orthography in
`lib/app/l10n/strings_tr.dart` before any release. It is one file, every
user-visible string is in it, and no other file contains player-facing text.
This is the highest-priority cosmetic fix in the repository.

## D-8: Difficulty levels exist but only the baseline is implemented

**Decision.** Ship the five-level enum and let the player choose, but implement
only `RandomLegalPolicy`, and state in the AI lab that the choice does not yet
change how opponents play.

**Why.** The alternatives were mapping all five levels onto one policy, which
would make the selector a lie, or hiding the levels, which would hide the
planned shape of the feature. Saying so plainly is the honest third option, and
no mode is playable in milestone 1 in any case.

## D-9: Seats are plain integers

**Decision.** A seat is an `int` plus a `SeatingPlan`, not a wrapper class.

**Why.** Seat values are compared and used as indices in the innermost loops of
Monte Carlo search. A wrapper there would mean millions of short-lived
allocations per decision, against an explicit requirement to avoid excessive
allocation in search loops. `SeatingPlan` range-checks at its boundary, so the
safety a wrapper would buy is still present where it matters.

## D-10: A bury profile starts from a deck that does not divide evenly

**Decision.** Three-player buried Batak uses the full 52-card deck. The
validator checks `deckSize - playerCount * tricksPerHand == cardsToBury`
rather than requiring an evenly divisible deck.

**Why.** An earlier draft stripped a card to make 51 divide by three *and* gave
the declarer a surplus card to bury, which is incoherent: a fully dealt
51-card deck leaves no surplus. The actual rule is that the odd card **is** the
surplus. Seventeen each uses 51 of 52, and the declarer takes the remaining one
and buries one. Modelling it this way makes `tricksPerHand` derive correctly
and gives the bury something to resolve.

## D-11: The table preview is driven by the real engine

**Decision.** `GameplayPreview` deals a seeded hand and plays two plies through
`TrickPlayEngine` rather than hand-assembling a mock position.

**Why.** A hand-written mock can describe a position the rules forbid, and the
layout would then be validated against something that can never occur. Driving
the real engine means the preview cannot be illegal, and it exercises the
legal-move highlighting against genuine output. The preview remains clearly
labelled non-playable: nothing advances and taps do nothing.

## D-12: Illegal moves abort a simulation run by default

**Decision.** `SimulationConfig.failOnIllegalMove` defaults to true, so the
first illegal command throws. Setting it false counts the attempt and continues
with the first legal card instead.

**Why.** Silently substituting a legal card would hide precisely the defect the
harness exists to catch, so the default fails loudly. The counting mode exists
because the benchmark protocol calls for an illegal-move *rate* across a batch,
which cannot be measured if the first one halts the run.

## D-13: Widget tests run at a portrait phone size, not the default viewport

**Decision.** `test/integration/app_navigation_test.dart` sets a 1080x2340
physical viewport at DPR 3 (360x780 logical) and scrolls lazily-built lists to
reach a target, instead of using `flutter_test`'s default 800x600.

**Why.** The product is locked to `portraitUp` in `main.dart`, so 800x600 is a
shape it can never run at, and it is wider than any phone. Three real layout
defects passed unnoticed at that size and appeared immediately at phone width:

- `SeatPanel`'s `Row` overflowed by 153 pixels. Three opponent panels share a
  phone's width, leaving each about 80 logical pixels, but the name and stat
  texts sized to their natural width. Fixed by putting the text column in an
  `Expanded` with single-line ellipsis.
- The AI lab report header `Row` overflowed by 46 pixels, for the same reason.
  Fixed with `Expanded`.
- `AppPanel` was built on `DecoratedBox` with a background colour, which hides
  the background and ink splashes of any `ListTile` inside it, because those
  paint onto the nearest `Material` ancestor. Every settings row would have
  given no visible tap feedback. Fixed by rebuilding `AppPanel` on `Material`
  with a `shape`, which fixes all ten call sites at once.

**Consequence.** Two testing rules follow. A widget below the fold in a lazy
list has never been built, so no finder can see it and `ensureVisible` cannot
reach it -- only dragging puts it in the tree. And a `.first`-narrowed finder
throws `Bad state: No element` rather than reporting empty, so finders passed
to `scrollUntilVisible` must be un-narrowed.

A third trap is worth recording: `harness()` returns a `const` widget, so
calling `pumpWidget` with it again in a loop reuses the same element tree and
the `Navigator` keeps the previous iteration's stack. Per-destination tests are
registered in a loop around `testWidgets` rather than looping inside one test.

**Open.** An 80-pixel opponent panel is too cramped for a name plus
"3 el  -  13 kart"; it now truncates rather than overflowing, which is correct
but not good. The seat panel needs a deliberate redesign (vertical stack, or
stats moved to a shared score strip) before any mode ships.

## D-14: Web is not a viable platform, because the domain owns a 64-bit PRNG

**Decision.** Android and iOS only. No `web/`, no `windows/`. An attempt to add
web for a quick visual preview was reverted.

**Why it cannot work.** `dart2js`/`dartdevc` compile Dart `int` to a JavaScript
`number`, which is a double with a 53-bit mantissa. `SeededRandom` is
xorshift64* with a SplitMix64 finalizer and depends on exact 64-bit wrapping
arithmetic. The compiler rejects the constants outright:

```
lib/core/util/seeded_random.dart:25:35: Error: The integer literal
0x9E3779B97F4A7C15 can't be represented exactly in JavaScript.
```

This is not a defect. It is the direct consequence of D-5, which chose to own
the generator so that reproducibility is a property of this repository rather
than of the SDK. Web support would require one of:

- reimplementing 64-bit arithmetic over 16-bit chunks (a 64x64 multiply needs
  16 partial products, because even a 32x32 product exceeds 2^53 on web) —
  exact, but fiddly and slow, on the most correctness-critical file here;
- `package:fixnum` `Int64`, which is emulated on every platform and would slow
  the native path that the benchmark harness depends on;
- a conditional import giving the VM native ints and web an emulation — two
  implementations of the determinism-critical path that **cannot be tested
  against each other on a single platform**.

All three trade real risk for a convenience on a platform the product never
targeted. Rejected.

**Consequence.** `flutter run -d chrome` fails to compile, by design. Seeing
the app run requires one of the two real targets:

| Target | Requirement |
|---|---|
| Android | A device with USB debugging, or an emulator (needs the WHPX Windows feature, which is disabled here) |
| iOS | macOS with Xcode. Cannot be built from Windows at all — Apple restriction |

A Windows desktop build was also considered, since `int` is a true 64 bits
there, but it needs Visual Studio with the C++ workload and that install is
blocked by policy on the development machine (the installer returns 16389 even
with an elevated token). Not pursued.

## D-15: A nullable field is cleared through an explicit flag, never by passing null

**Decision.** Where `copyWith` covers a nullable field, clearing it takes a
separate boolean: `RuleProfile.copyWith(clearFixedTrump: true)`,
`SpadesBatakMatchState.copyWith(clearHand: true)`. Passing `null` means "leave
it alone", which is what `field ?? this.field` already does.

**Why.** The idiomatic one-liner cannot distinguish the two intents, so
`copyWith(fixedTrump: null)` silently kept the old trump. That is worse than a
compile error: the call looks correct and does nothing.

**How it was found.** A Koz Maca test tried to build a profile with no fixed
trump to check that the engine refuses it. The test failed because the engine
*correctly* accepted a profile that still had its trump. Chasing it showed the
real damage: `RuleProfileValidator` has branches for `bidding.no_trump_source`
and `king.missing_rules`, and **neither had a test**, because the condition
could not be constructed through `copyWith` at all. Two error paths were
unverified.

**Consequence.** Both branches now have tests, and so does the trap itself:
`copyWith(fixedTrump: null)` must preserve the value while
`copyWith(clearFixedTrump: true)` must clear it. That second test exists so
nobody later "fixes" `copyWith` to treat `null` as clearing and silently
changes the meaning of every existing call.

## D-16: Suit pips are painted, not typed

**Decision.** `SuitPip` draws the four suits as paths. `Suit.symbol` keeps its
Unicode character for logs, diagnostics and `PlayingCard.label`, but nothing a
player looks at renders a pip as text.

**Why.** U+2660..U+2667 are not in Roboto. A device shows them only if the
system fallback chain happens to supply them, and that chain is not something
this project controls or can test on every device it ships to. A card game
whose suits might not render is not a risk worth carrying for four shapes.

**How it was found.** The headless screenshot harness rasterises with the
fonts it is given and no system fallback, so every pip came out as an empty
box, on the cards and in the trick area alike. That is the harness's limitation
rather than proof the app is broken on a phone, but it demonstrates exactly
what a device without the glyphs would do.

**Consequence.** Pips scale crisply to the corner index and the watermark from
one set of control points, and they take a colour, so a four-colour deck is a
parameter rather than a new font.

## D-17: A button's `textStyle` replaces the label style, so it must be merged first

**Decision.** `AppTheme.dark` merges the custom `TextTheme` onto
`Typography.material2021(platform: defaultTargetPlatform).white` before the
button themes read it, rather than handing the button themes the raw styles.

**Why.** `ThemeData` merges typography under whatever `textTheme` it is given,
which is where the font family comes from. A `ButtonStyle.textStyle` is applied
to the label directly and *replaces* its style, so a style assembled without a
family -- as every style in `_textTheme()` is -- drops the family that the
merge would have supplied and the label falls back to the platform font.

**How it was found.** Twice. First on app bar titles, where `titleTextStyle`
was being set from the raw style; the fix there was to delete the override and
let Material 3 default to the merged one. Then on every button in the app: the
screenshot harness, which has no system font to fall back to, rasterised
`Basla`, `Sonraki dagitim` and the rest as rows of empty boxes while all other
text rendered correctly. The same defect on iOS is quieter and still wrong: San
Francisco button labels under Roboto body text.

**Consequence.** Styles handed to a `ButtonStyle`, a `SnackBarThemeData` or
anything else that replaces rather than merges must come from the merged theme.
The screenshot harness is what makes this class of defect visible at all, since
on Android the fallback happens to be Roboto and the bug is invisible.

## D-18: One plugin, one storage mechanism: JSON files under `path_provider`

**Decision.** `path_provider` is the app's only platform plugin. Everything
stored -- preferences, the match in progress, the match history -- is a JSON
file this app writes and reads itself, through `JsonFileStore` in
`lib/platform/`. No key-value plugin, no database.

**Why.** The plugin answers one question, "where may this app write?", and
nothing else: it opens no socket and requests no permission, so the offline
requirement is untouched. A key-value plugin would answer a question the app
also has, but it would not remove the need for files -- the match history is a
list, and the save is a document -- so it would add a second mechanism rather
than replace one.

**Why files rather than a database.** The whole store is three documents, read
whole and written whole. A database would add a schema, a migration story and
a query language for data that is never queried.

**Consequences.**

* `lib/core` still imports no `dart:io`. The file system lives in
  `lib/platform/`, behind the repository interfaces the domain declares, which
  is what keeps every test and the screenshot harness running on memory-backed
  implementations that touch no disk.
* Writes are atomic by rename. A game that autosaves after every card will be
  killed mid-write eventually; without the rename that would leave a truncated
  file where the save used to be, and the player would lose the match rather
  than one move of it.
* Storage failures never reach the table. A match that cannot be saved is
  still a match that can be played.

## D-19: A match is saved as a move log, not as a position

**Decision.** `SavedMatch` stores the rule profile, the deal seed and every
card played in order. Resuming replays the log through the engine
(`SpadesBatakRestore`). Schema 1, which held a position summary and no log,
is refused rather than migrated; nothing ever wrote one, because no mode was
playable.

**Why.** A log cannot describe a position the rules would not allow: every
move goes back through the engine's own validation on the way in. A snapshot
can, and nothing would notice -- a hand-edited file would load as a plausible
but illegal game. The log is also smaller, and it stays valid as the state
types grow, where a serialised snapshot would need a migration per change.

**What makes it work.** The domain is deterministic and hand `i` is dealt from
`baseSeed + i`, so the same seed and the same moves reconstruct the same
position exactly -- including the cards in the hands nobody has seen.

**Consequence.** The save carries the hand count and the score as well, purely
so the home screen can draw its resume card without replaying. The replay is
what decides the real values, and a disagreement means the file was edited or
truncated, so the save is dropped. `tool/checks/save_roundtrip.dart` exercises
all three paths: an intact save restores identically, a truncated log is
refused, and an edited score is refused.
